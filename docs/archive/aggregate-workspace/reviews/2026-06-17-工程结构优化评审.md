# EmbeddedBrowser 工程结构优化评审

> 历史评审说明：本报告反映当时工程状态，不作为 IPC v2 当前设计规范。
> 当前设计入口见 `../design/architecture.md`。

## 评审范围

本次评审覆盖聚合工作区 `E:\Repositories\unity\Packages\EmbeddedBrowser` 下的主要子系统：

- `BrowserRenderer`：Unity 端包、配置、脚本结构、仓库治理。
- `headless_browser`：Rust CEF 浏览器进程、共享内存协议、发布产物、crate 结构。
- `HeadlessBrowser`：旧 .NET 浏览器进程与当前 Rust 主链路的共存边界。
- `docs/` 与聚合根：跨仓文档、评审报告、发布物归属。

本次只做只读评审和报告落地；未启动 Unity Editor，未执行 Unity batchmode，未执行 `dotnet build` / `msbuild` 编译 Unity 生成项目，未运行会写入 `target` 的 Cargo 构建、测试或 clippy 命令。

## 总体结论

当前运行效果已经可用，但工程结构还没有完全收口。最需要优先处理的不是继续改渲染细节，而是把“浏览器进程发布物、Unity 默认配置、共享内存协议、旧 .NET 与 Rust 主链路”这几条边界固定下来。否则后续每次性能、启动、协议或发布问题都会在多个仓库之间互相误导。

当前建议按以下优先级推进：

- 先收口发布物和配置：不要让已跟踪的 Unity 配置指向另一个子仓未跟踪的本机 `dist`。
- 再统一协议文档：Capture v2、dirty rect、ack sequence、MouseState 字节数必须只有一个权威定义。
- 然后确定主实现：Rust 是当前主链路时，旧 .NET 应标记为参考/归档/回退实现，README 和默认路径要同步。
- 最后做代码结构拆分：Rust `main.rs`、Unity `BrowserStatic` 这类入口层已经承载过多职责，适合分层整理。

## 高优先级问题

### 发布物边界不成立

证据：

- `BrowserRenderer/BrowserConfig.json:2` 指向本机绝对路径 `E:/Repositories/unity/Packages/EmbeddedBrowser/headless_browser/dist/win-x64/headless_browser.exe`。
- `git -C headless_browser status --short` 显示 `?? dist/`，`git -C headless_browser ls-files dist` 为空。
- `headless_browser/dist/win-x64` 当前包含 `libcef.dll`、`locales/`、`*.pak`、`headless_browser.exe`、`headless_browser.pdb` 和 `debug.log`，其中 `libcef.dll` 约 257 MB。
- `headless_browser/.gitignore:2` 只忽略 `/target/`，`headless_browser/.gitignore:15` 只忽略 `*.pdb`，没有定义 `dist/` 治理策略。

风险：

Unity 子仓提交了一个依赖另一个子仓本机未跟踪产物的路径。换机器、清理工作区、切分仓库或 CI 发布时，默认配置不可复现。`debug.log` 这类运行时噪声也可能混入发布包或误提交。

建议：

- 明确 `headless_browser/dist/` 是本地生成物还是正式交付物。
- 如果是本地生成物：加入 `.gitignore`，Unity 只提交 `BrowserConfig.example.json` 或相对占位配置，真实路径走本地覆盖、环境变量或运行目录配置。
- 如果是正式交付物：不要普通提交整包；应走 release artifact、制品库或 LFS，并补版本号、平台目录、校验和和生成脚本。
- `debug.log`、临时 PDB 和本地诊断文件不得进入正式发布目录。

### Unity 默认配置提交了本机路径和非文档化枚举

证据：

- `BrowserRenderer/BrowserConfig.json:2` 是绝对路径。
- `BrowserRenderer/BrowserConfig.json:3` 是 `"GraphicsMode": "True"`。
- `BrowserRenderer/README.md:230-235` 示例和说明只写 `Auto`、`Off`、`On`。
- `BrowserRenderer/Assets/Packages/Scripts/BrowserHandler.cs:42` 有归一化入口，但 README 未说明 `True` / `False` 的兼容语义。
- `git -C BrowserRenderer ls-files BrowserConfig.json` 显示该配置文件已被 Git 跟踪。

风险：

配置 schema 和实际值不一致，后续排查 GPU/WebGL 行为时容易出现“代码兼容了但文档不承认”的偏差。本机绝对路径也会让其他开发者拉仓后默认不可运行。

建议：

- 仓库内保留 `BrowserConfig.example.json` 或可提交的默认模板，不提交个人机器路径。
- `GraphicsMode` 统一为明确枚举：`Auto`、`Off`、`On`。
- 若继续兼容 `True` / `False`，需要在 README 和配置校验里显式声明映射关系，例如 `True -> On`、`False -> Off`。

### 共享内存协议文档和实现不一致

证据：

- `headless_browser/PROTOCOL.md:186-248` 仍以简单 Capture 帧示例描述 `[width, height, pixels]`。
- `headless_browser/src/modules/capture.rs:19-27` 已实现三槽、32 字节 header、dirty rect、ack sequence。
- `headless_browser/src/modules/capture.rs:138-166` 写入 `ack_sequence`、`frame_type`、`rect_count`、`payload_size` 等字段。
- `headless_browser/src/modules/protocol.rs:394-403` 仍保留旧的 `CaptureFrame` 概念，容易和 Capture v2 混淆。
- `BrowserRenderer/README.md:101` 仍写 `Operate` 鼠标位置状态为 5 字节；`headless_browser/PROTOCOL.md:27` 与 `headless_browser/src/modules/protocol.rs:154-179` 是 6 字节 `MouseState`。
- `headless_browser/DEVELOPMENT.md` 仍保留旧的简单帧布局说明。

风险：

Unity 和浏览器进程通过字节级协议耦合，文档漂移会直接导致后续实现按不同布局演进。Capture 这条链路刚经历过性能和撕裂问题，协议必须可审计、可回归、可对照。

建议：

- 建立单一权威协议文档，明确 Capture v2 header：宽、高、slot、sequence、frame type、dirty rect count、payload bytes、ack sequence。
- 明确 full frame 与 dirty frame payload 布局，写清 dirty rect header 和逐行 BGRA 数据顺序。
- MouseState、MouseEvent、Heartbeat、HandlerCommand 等也统一字段表和字节数。
- 增加 Rust/Unity 都能对照的协议样例字节测试，避免只靠 README 人工同步。

### 旧 .NET 和 Rust 浏览器主链路未明确

证据：

- `BrowserRenderer/BrowserConfig.json:2` 当前指向 Rust `headless_browser/dist/.../headless_browser.exe`。
- `BrowserRenderer/README.md:212-217` 仍描述依赖 `.NET 8.0` 和 `CefGlue` 的 `HeadlessBrowser.exe`。
- `headless_browser/README.md:3` 声明 Rust/CEF 实现。
- `HeadlessBrowser/HeadlessBrowser/HeadlessBrowser.csproj` 仍存在并维护 `CefGlue.Common`、`MemoryStacks` 等依赖。

风险：

两个浏览器实现并存本身不是问题，但当前默认配置、README、发布路径没有明确“谁是主链路”。这会导致协议改动、性能测试、发布打包、回归定位时在旧实现和新实现之间来回切换。

建议：

- 在聚合根或正式主仓文档中明确：当前主链路是 Rust `headless_browser`。
- `.NET HeadlessBrowser` 标记为参考实现、回退实现或归档实现，并写清是否还要保持协议同步。
- `BrowserRenderer` README 的外部依赖、路径示例和发布说明改为 Rust 主链路；如保留 .NET 路径，应放到“旧实现/回退实现”章节。

## 中优先级问题

### Rust 入口层职责过重

证据：

- `headless_browser/src/main.rs` 约 966 行。
- 同一文件内包含 Unity handler 主循环 `run_unity_handler_mode`、心跳观察 `observe_heartbeat`、命令处理 `handle_unity_command`、CLI 解析 `parse_args_from`、graphics mode 解析、heartbeat watchdog、single instance lock、run log、Ctrl+C handler 等职责。
- 典型位置包括 `src/main.rs:111`、`src/main.rs:215`、`src/main.rs:229`、`src/main.rs:436`、`src/main.rs:553`、`src/main.rs:863`。

风险：

入口层同时承担协议调度、生命周期、配置解析和平台锁，后续修复某条链路时容易牵连其他路径。当前项目已经出现过性能、退出、启动、协议同步连续调整，入口层需要降低耦合。

建议：

- `main.rs` 保留参数解析和启动组合。
- 拆出 `cli`、`unity_handler`、`heartbeat`、`graphics_mode`、`process_lock`、`run_log` 等模块。
- handler loop 的单元测试跟随模块迁移，保持现有测试覆盖。

### Rust crate 公共 API 暴露过宽

证据：

- `headless_browser/src/lib.rs:36-38` 公开 `browser`、`ipc`、`modules`。
- `headless_browser/src/browser/mod.rs:8-11` 公开 `cef_app`、`PageHandler`、`OsrRenderHandler` 等内部 CEF 适配。
- `headless_browser/src/modules/mod.rs:16-26` 公开多个内部模块和协议类型。
- `headless_browser/Cargo.toml:9-10` 同时声明 `cdylib` 和 `rlib`，但当前只看到极简 FFI 入口，未看到稳定 C ABI 调用方。

风险：

内部实现细节成为公共 API 后，后续重构成本会被放大。`cdylib` 产物如果不是当前真实交付物，也会带来命名、脚本、发布说明漂移。

建议：

- 收缩 `pub mod` 和 `pub use`，只导出当前实际调用方需要的最小接口。
- CEF handler、render handler、shared memory wrapper 默认保持 crate 内部。
- 如果 `cdylib` 暂无真实调用方，移除或标记为后续目标；如果需要保留，补稳定 ABI 文档和产物命名。

### Unity 端运行时生命周期集中在 MonoBehaviour

证据：

- `BrowserRenderer/Assets/Packages/Scripts/BrowserStatic.cs` 同时负责单例、进程启动、Update 轮询、共享内存任务、异常退出重启、销毁路径。
- `BrowserStatic.cs:151` 附近存在通用 `MemoryStackTask` 调度。
- `BrowserRenderer/Assets/Packages/Scripts/PageHandler.cs:64-71` 直接启动多个内存模块。

风险：

MonoBehaviour 绑定 Unity 生命周期是必要的，但把进程生命周期、重启策略、协议任务调度都放在运行时组件里，会让逻辑难以脱离 Unity 做单元测试，也会让退出和重启问题更难审计。

建议：

- 把浏览器进程生命周期、重启策略、协议任务编排拆成普通 C# 服务类。
- MonoBehaviour 只负责挂载、Unity 生命周期桥接和主线程调度。
- 对 handler command、heartbeat、process exit signal 做不依赖 Unity Editor 的单元级测试。

### Unity 仓库治理规则不完整

证据：

- 本地存在 `BrowserRenderer/Library`、`Temp`、`Logs`、`UserSettings` 等 Unity 生成目录。
- `BrowserRenderer/.gitignore` 当前覆盖 `.vs/`、`*.csproj`、`*.sln`、`Exports/` 等，但没有显式覆盖 `Library/`、`Temp/`、`Logs/`、`UserSettings/`、`Obj/`、`Build/`、`Builds/`。
- `git -C BrowserRenderer ls-files Library Temp Logs UserSettings` 当前为空，说明尚未误跟踪，但规则依赖外部或手工习惯。
- `BrowserRenderer/.gitattributes` 只配置 LFS，没有 Unity YAML 资产的 text/eol/merge 策略。

风险：

当前还没污染版本库，但项目级规则不完整。换机器或新成员加入时，Unity 生成目录和 YAML 资产冲突治理容易出问题。

建议：

- 在 `.gitignore` 显式补齐 Unity 生成目录。
- 在 `.gitattributes` 补 Unity 文本资产规则，例如 `.unity`、`.prefab`、`.asset`、`.mat`、`.meta`、`.asmdef`、`.json` 的文本和换行策略。
- 是否启用 `unityyamlmerge` 可按团队工具链决定，但至少要有明确合并策略。

### README 和依赖清单漂移

证据：

- `BrowserRenderer/README.md:205-208` 只列出部分 Unity 依赖。
- `BrowserRenderer/Packages/manifest.json:3-13` 还包含 `com.kimotech.plugin.srdebugger`、`org.nuget.globalconfigs`、`org.nuget.memorystacks`、`org.nuget.singletons`、`org.nuget.superevents`、toolchain/sysroot 等依赖。
- `headless_browser/README.md:37` 仍写 `headless_browser_rust/`。
- `headless_browser/src/lib.rs:17` 示例仍引用 `headless_browser_rust`。
- `headless_browser/build.ps1:79-83` 查找 `headless_browser_rust.dll`，而包名和二进制名是 `headless_browser`。

风险：

文档不是单纯描述问题，这里会直接影响构建、发布和排查。尤其是 Rust 主链路刚切换完成，旧命名和旧依赖说明会让后续验证走错路径。

建议：

- README 明确以 `Packages/manifest.json` 和 `Cargo.toml` 为准。
- 区分运行时依赖、调试依赖、编辑器依赖、跨平台 toolchain。
- 统一 `headless_browser` / `headless_browser_rust` / `HeadlessBrowser` 命名，保留旧名时必须说明兼容原因。

## 建议落地顺序

### 发布和配置收口

- 定义 `headless_browser/dist` 的归属。
- 清理或忽略 `debug.log` 等运行时产物。
- 将 `BrowserConfig.json` 改为模板或本地覆盖机制。
- 统一 `GraphicsMode` schema。

### 协议文档收口

- 更新 `headless_browser/PROTOCOL.md` 为 Capture v2。
- 修正 `BrowserRenderer/README.md` 中 `Operate` / `MouseState` 字节数。
- 清理 `headless_browser/DEVELOPMENT.md` 和旧 README 中的旧帧布局。
- 增加协议样例测试。

### 主链路声明

- 明确 Rust 为当前主浏览器进程。
- 给 .NET `HeadlessBrowser` 标注当前状态和维护边界。
- BrowserRenderer README 改成 Rust 发布路径，旧 .NET 路径放入回退说明。

### 代码结构拆分

- Rust 先拆 `main.rs`，不要先动 CEF 逻辑。
- Unity 先抽进程生命周期和协议调度服务，不先改渲染行为。
- 公共 API 收缩放在功能稳定后做，避免和当前调试链路混在一起。
