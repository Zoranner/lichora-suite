# EmbeddedBrowser 浏览器交互性能重构评审报告

> 历史评审说明：本报告用于保留卡顿问题证据和旧链路分析，不是 IPC v2 的当前设计规范。
> 当前设计入口见 `../design/architecture.md`。

## 评审范围

本次评审覆盖 `E:\Repositories\unity\Packages\EmbeddedBrowser` 聚合工作区中的两个主链路子仓：

- `BrowserRenderer`：Unity 端页面组件、输入桥接、共享内存读取、纹理显示和浏览器进程生命周期。
- `headless_browser`：Rust/CEF 浏览器进程、handler 模式、输入轮询、OSR paint、Capture v2 共享内存发布和协议文档。

参考项目为 `E:\Repositories\projects\Zoranner\wincast-suite`，只借鉴其 latest-only、backpressure、状态计数、输入所有权和 runtime 边界思想，不评价 wincast 业务功能，也不把 H.264/TCP 推流链路直接迁入本项目。

本次没有启动 Unity Editor、Unity batchmode、BuildPipeline，也没有运行 `dotnet build` / `msbuild` 编译 Unity 生成项目。结论来自源码、配置、文档、当前 Git 状态和已执行的 Rust/CSharpier 检查结果。

## 当前结论

当前卡顿问题已经不是某个鼠标写入函数能解决的级别。现有架构把输入、CEF message loop、OSR paint、共享内存发布、Unity 主线程纹理拷贝和 `Texture2D.Apply(false)` 串在一条强耦合链路里；慢消费者时既缺少清晰 backpressure，又缺少真实状态计数，导致问题表现为鼠标延迟、轨迹成批出现、画面撕裂和重启后状态难定位。

重构目标应收敛为：

- Rust 端：拆开 `OnPaint` 和 Capture 共享内存发布，让 CEF 回调变轻；把 `BrowserEntry` 的生命周期、输入、repaint、capture 状态拆成更明确的 owner。
- Unity 端：把 `LateUpdate` 内的输入、capture copy、texture apply、IME/keyboard 调度拆成有预算的 latest-only 消费模型；明确 ack 到底代表 copy 还是 apply。
- 协议层：两端都用类型化读写结构表达 `HandlerCommand`、`Heartbeat`、`CaptureHeader`，不要继续分散手写 offset。
- 观测层：建立真实计数，区分 submitted、published、copied、applied、acked、dropped、input consumed，不用假计数掩盖链路状态。

## 关键证据

### Rust 端

`headless_browser/src/main.rs` 的 handler 模式同时负责打开 `Handler.{guid}` / `HEARTBEAT.{guid}`、维护 `HashMap<String, BrowserEntry>`、读取命令、推进所有 browser 的 `do_message_loop_work()`。这个 loop 目前是多 browser 串行调度，单个 browser 的 paint、close、repaint 或输入处理变慢会影响同进程其他 browser。

`headless_browser/src/browser/entry.rs` 的 `BrowserEntry` 同时持有 CEF browser/client/app、render handler、capture/caret/surrounding text、keyboard/mouse/IME/script 模块、repaint/probe 状态和 close 状态。它已经承担了实例生命周期、输入所有权、message pump、repaint loop 和脚本探测，职责过宽。

`headless_browser/src/browser/render.rs` 的 `on_paint_impl()` 在 CEF paint 回调内把 buffer 转 slice，然后锁 `CaptureModule` 并调用 `write_paint_frame()`。`headless_browser/src/modules/capture.rs` 在这条路径里完成 dirty payload 构建、slot 写入、header 写入和 flush。即使已加入未 ack 丢帧，`OnPaint` 仍承担过多同步发布成本。

`headless_browser/src/ipc/shared_memory.rs` 同时提供普通事件写入、旧 frame helper、offset payload 写入、length header 和 flush 操作。Capture v2 和旧 `[width,height,pixels]` helper 并存，协议边界不够清晰。

### Unity 端

`BrowserRenderer/Assets/Packages/Scripts/PageRenderer.cs` 的 `LateUpdate()` 串行执行 browser restart、size check、mouse state、main thread update、capture copy、`Texture2D.Apply(false)`、scroll reset、Linux IME、keyboard、IME。输入与画面消费在同一帧预算里互相影响。

`BrowserRenderer/Assets/Packages/Scripts/MemoryModules/CaptureSharedMemory.cs` 在 `TryCopyCommittedSlotOnce()` 中读取 header、拷贝 full/dirty payload、二次校验 header，然后立即 `WriteAckSequence()`。但是 `PageRenderer` 随后才调用 `ApplyTexture()`。这意味着当前 ack 表示 CPU copy 完成，不表示 Unity texture apply/GPU 上传完成。

`BrowserRenderer/Assets/Packages/Scripts/MemoryModules/CaptureModule.cs` 维护 `_LastCaptureSequence` 和 frame version，但 Unity 侧没有成体系的 copied/applied/dropped/ack lag 计数。性能排查只能靠用户体感、日志和局部 frame version 推断。

`BrowserRenderer/Assets/Packages/Scripts/BrowserStatic.cs` 和 `ProcessHandler.cs` 负责进程启动、退出监听、重启、页面注册和重发 AddPage。当前能用，但缺少 restart generation 和结构化状态快照，旧共享内存、旧 PageHandler、进程退出原因和页面恢复状态难区分。

## wincast 可借鉴内容

### 可迁移

- Runtime 作为生命周期边界：用明确 runtime owner 管理状态、最新帧、输入队列、listener/process 和 shutdown 顺序。
- latest-only frame：生产端只提交最新帧，消费端按 sequence 跳过旧帧，不追帧。
- 真实丢帧计数：用 submitted/published/sent/dropped/received input 等真实链路事件计数，不提前占位假字段。
- 输入按状态和事件分流：鼠标移动可以 latest-only，点击、滚轮、键盘、IME commit 必须按事件语义限额或背压。
- 状态快照：给 Unity 和 Rust 都提供可以读取的 runtime/page/capture/input 状态，避免只靠日志。

### 不应迁移

- 不迁移 H.264 编码链路。当前是同机 Unity 嵌入浏览器，主要瓶颈是 CEF paint、共享内存写入、Unity copy/apply，不是网络传输。
- 不迁移 TCP/JSON framed session。现有 MemoryStacks + Handler/Capture/Input 协议更贴合本机大帧共享。
- 不迁移 wincast 的单客户端语义。`EmbeddedBrowser` handler 模式天然支持多页面，应保留多 `BrowserEntry`。
- 不迁移 Unity final frame capture。wincast 捕获 Unity 最终画面；本项目是 CEF OSR 画面进入 Unity UI。

## 重构切片

### 切片一：协议和状态先类型化

目标：不改行为，先收口 offset、常量和状态口径。

建议范围：

- Rust：`src/modules/protocol.rs`、`src/modules/capture.rs`、`src/main.rs`。
- Unity：新增或整理 `HandlerCommandWriter`、`CaptureHeader`、`HeartbeatPayload` 这类纯协议类型，替代 `BrowserStatic.cs`、`CaptureSharedMemory.cs` 中分散的 offset。
- 文档：同步 `PROTOCOL.md`、`DEVELOPMENT.md`、`BrowserRenderer/README.md`。

验证：

- Rust 单测覆盖 handler command、capture header、ack/drop 分支。
- C# 运行 CSharpier check 和文本级协议一致性检查。
- 不需要 Unity 内验证。

风险：

- 不能顺手改协议布局。
- 当前 README 仍有未 ack 回退 full frame 的旧描述，需要先修正，避免后续按旧文档回退。

### 切片二：引入真实遥测

目标：让卡顿可定位，不再靠体感判断。

建议指标：

- `capture_submitted_frames`：CEF `on_paint` 进入次数。
- `capture_published_frames`：成功写入 Capture header 的次数。
- `capture_not_acked_skips`：因上一帧未 ack 且非 resize 被丢弃的次数。
- `capture_full_frames` / `capture_dirty_frames` / `capture_payload_bytes`。
- `unity_capture_copied_frames` / `unity_texture_applied_frames` / `unity_ack_written_frames`。
- `input_mouse_state_writes` / `input_mouse_state_skips` / `input_event_sent` / `input_event_backlog`。
- `handler_restart_count` / `handler_exit_code` / `heartbeat_age_ms` / `pages_registered` / `pages_active_in_rust`。

验证：

- Rust 单测验证计数只在真实事件发生时递增。
- Unity 源码检查和 CSharpier check。
- 用户实测时读取日志或状态输出，判断瓶颈是 submitted 多、published 少、copied 少还是 applied 少。

风险：

- 不允许先放永远为 0 的假字段。wincast 已经踩过假 `dropped_frame_count` 的坑。

### 切片三：Unity 端 frame budget 和 ack 语义

目标：主线程每帧只做有预算的最新帧消费，不追旧帧。

建议范围：

- `PageRenderer.cs`
- `MemoryModules/CaptureModule.cs`
- `MemoryModules/CaptureSharedMemory.cs`

建议行为：

- `CaptureReader` 先读取最新 header/sequence，再决定是否 copy。
- 每帧最多一次 copy/apply，超预算直接跳到最新 sequence。
- 明确 ack 是 copy ack 还是 apply ack。更稳的语义是 Unity 决定接受并完成 apply 后再 ack，或者增加 copied/applied 两级状态。
- resize/full frame 作为例外处理，不能因为未 ack 卡死在旧尺寸。

验证：

- CSharpier check、diff check。
- 用户 Unity 内验证普通页面、WebGL 页面、鼠标轨迹测试、窗口 resize。

风险：

- 如果 ack 延后到 apply 后，dirty frame 的门控会更严格，必须和 Rust Capture backpressure 同步。
- `Texture2D.Apply(false)` 仍是主线程成本，短期只能预算和丢帧，不能消除成本。

### 切片四：Rust Capture publisher

目标：让 CEF `OnPaint` 变轻，避免在 paint 回调内承担完整共享内存发布。

建议范围：

- `src/browser/render.rs`
- `src/modules/capture.rs`
- 新增 `src/modules/capture_publisher.rs` 或同等职责模块

建议行为：

- `on_paint` 只提交 latest frame 或做最小必要 copy。
- publisher 根据 ack、resize、dirty/full 策略写 Capture 共享内存。
- publisher 负责 published/drop/ack-lag 计数。

验证：

- Rust 单测覆盖 latest frame 覆盖、drop、resize full、dirty payload。
- `cargo fmt --all`
- `cargo clippy --all-targets --all-features -- -D warnings`

风险：

- CEF buffer 生命周期短，异步化必须复制像素或明确所有权。不能把 CEF 提供的临时 pointer 直接交给后台线程。

### 切片五：输入所有权拆分

目标：输入不再藏在 `BrowserEntry` 大对象里，状态输入和事件输入分开治理。

建议范围：

- `src/browser/entry.rs`
- `src/modules/mouse_state.rs`
- `src/modules/mouse_event.rs`
- `src/modules/keyboard.rs`
- `src/modules/ime.rs`
- `src/modules/script.rs`

建议行为：

- 抽 `BrowserInputOwner::poll(host, browser, loading)`。
- MouseState 保持 latest-only。
- MouseEvent/Keyboard/IME/Script 保持事件语义，增加预算、backlog、消费计数。
- 保留 IME 对 keyboard/module 状态的依赖，不能机械拆散。

验证：

- Rust 单测覆盖 poll 顺序、mouse state latest-only、event ack/clear。
- Unity 侧实测鼠标、滚轮、键盘、中文 IME。

风险：

- 点击、键盘、IME 不能像 MouseMove 一样丢弃；只能合并、限额、背压或记录失败。

### 切片六：handler runtime 和生命周期 generation

目标：从 `main.rs` / `BrowserStatic.cs` 中拆出 runtime owner，解决重启和旧状态残留难定位。

建议范围：

- Rust：`src/main.rs` 拆出 `runtime.rs`、`handler.rs` 或同等模块。
- Unity：`BrowserStatic.cs` 拆出 `BrowserRuntimeController`、`ProcessSupervisor`、`PageRegistry`。
- 共享内存：必要时给 handler/page/capture 增加 generation 或状态版本。

验证：

- Rust handler command fake tests。
- Unity 源码检查、CSharpier check。
- 用户实测进程崩溃重启、Play Mode 退出、频繁 Add/Remove 页面。

风险：

- 不要在这个阶段同时改 CEF 初始化和 Capture 协议，否则失败定位会失控。
