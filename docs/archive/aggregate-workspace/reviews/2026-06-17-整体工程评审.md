# EmbeddedBrowser 整体工程评审报告

> 历史评审说明：本报告反映当时工程状态，不作为 IPC v2 当前设计规范。
> 当前设计入口见 `../design/architecture.md`。

## 评审范围

本次评审对象是 `E:\Repositories\unity\Packages\EmbeddedBrowser` 聚合工作区，覆盖：

- `BrowserRenderer`：Unity 端包、运行时代码、共享内存接入、进程生命周期和资源/包治理。
- `HeadlessBrowser`：.NET 8 + CefGlue 浏览器进程、渲染/输入/生命周期链路和测试入口。
- `native-ime`、`BrowserRenderer/NativePlugins/process-spawner`：Rust 子项目的基础治理和格式检查。
- `headless_browser`：旧 Rust 浏览器实现的仓库边界和产物治理风险。

本报告只评审工程体系、架构边界、质量门禁和风险，不评价功能需求完成度、场景视觉效果或某个测试网页本身是否正确。

## 评审依据

- 通用工程评审基线：仓库边界、产物治理、文档一致性、格式检查、测试入口、提交可追溯性和模块边界。
- Unity 工程评审基线：`Assets/` 目录、UPM 包依赖、asmdef、Runtime/Editor 分离、MonoBehaviour 职责、Unity 特殊目录和资源治理。
- .NET 工程评审基线：项目边界、nullable/analyzer、构建测试入口、生命周期、配置、日志和测试覆盖。
- Rust 工程评审基线：Cargo workspace、`target/` 产物治理、`cargo fmt --check`、crate 边界和文档状态。
- 项目现场规则：禁止启动 Unity Editor/batchmode/BuildPipeline；禁止用 Unity 生成 `.csproj/.sln` 做外部编译验证；C# 格式以 CSharpier 为准。
- 当前仓库事实：根目录不是单一 Git 仓库，`BrowserRenderer`、`HeadlessBrowser`、`MemoryStacks`、`native-ime` 等边界独立。

Context7 查询 CefGlue 线程模型时因额度耗尽未取得外部文档，因此本报告中关于鼠标移动线程边界的结论只基于本项目内部证据和相邻代码一致性判断。

## 总体结论

当前工作区的主要风险不在 `BrowserConfig.json`、`vSyncCount` 或默认场景这类 Unity 项目配置，而在浏览器输入、渲染和生命周期主链路的结构边界。最需要优先处理的是：Headless 侧鼠标移动高频路径没有和点击/滚轮一样进入 CEF UI 线程；Capture 发布把跨进程锁竞争直接转化为丢帧；关闭时先释放 Capture 再关闭 CEF browser，存在回调访问已释放对象的竞态。这几项能直接解释鼠标轨迹延迟、不跟手、画面新旧数据混合和退出残留风险。

工程治理层面，`BrowserRenderer` 的 UPM package 依赖清单与实际代码引用不一致，Runtime assembly 为一个共享内存模块打开了全局 unsafe，`PageRenderer` 承担了过多生命周期和协议职责。`HeadlessBrowser` 的 README 仍残留 CefSharp、旧 MemoryStacks 版本和旧渲染管线描述，测试入口也没有覆盖真实跨进程 capture/mouse/lifecycle 主链路。

## 主要问题

### 鼠标移动高频路径没有统一进入 CEF UI 线程

定性：违反硬性工程基线。

证据：

- `HeadlessBrowser/HeadlessBrowser/Modules/MouseStateModule.cs:86` 直接调用 `browserHost.SendMouseMoveEvent(mouseEvent, false)`。
- `HeadlessBrowser/HeadlessBrowser/Modules/MouseEventModule.cs:73` 的点击/滚轮路径使用 `CefRuntime.PostTask(...)` 投递。
- `HeadlessBrowser/HeadlessBrowser/PageHandler.cs:467` 已有 `PostToCefUiThread` 封装，说明项目本身已经承认 CEF UI 线程边界。

风险：

鼠标移动是最高频输入路径，直接从轮询任务调用 CEF 输入接口，会和点击/滚轮形成不同线程模型。该问题与鼠标轨迹延迟、不跟手、几秒后集中出现的现象高度相关。即使 CEF 某些平台上偶尔容忍跨线程调用，这种不一致也会让延迟、乱序和平台差异变得不可控。

建议：

把 `MouseStateModule` 的 mouse move 统一投递到 CEF UI 线程，并且不要把每个历史 mouse move 都排队。这里应该做 latest-only 合并：后台轮询只更新最新位置，CEF UI 线程一次只消费最新坐标，避免 UI 线程被旧 mouse move 淹没。

### Capture 写帧把共享内存锁竞争直接转化为丢帧

定性：违反硬性工程基线。

证据：

- `HeadlessBrowser/HeadlessBrowser/PageHandler.cs:295` 的 `OnPaint` 是 CEF paint 回调入口。
- `HeadlessBrowser/HeadlessBrowser/CaptureSharedMemory.cs:90`、`:149`、`:295` 进入写帧、写 dirty rect、ack 查询时都走 `TryEnterCaptureLock()`。
- `HeadlessBrowser/HeadlessBrowser/CaptureSharedMemory.cs:93`、`:152`、`:298` 拿不到锁直接 `return false`。
- `HeadlessBrowser/README.md:175` 明确写出“拿不到 Capture 互斥锁时直接丢弃当前 paint”。

风险：

Unity 读帧/写 ack 与 Headless 写帧竞争时，CEF paint 会被丢弃。鼠标移动会触发高频 repaint，这种策略会把交互高峰期变成跳帧、持续延迟和轨迹不连续。它也解释了“不是卡住后瞬间刷新，但仍然延迟、不跟手”的状态。

建议：

不要让 CEF paint 回调直接承担跨进程共享内存锁策略。更稳的结构是：paint 回调只把当前 CEF buffer 复制到进程内 latest buffer 或有界环形缓冲；独立发布器负责尝试写共享内存，写不进去时覆盖旧待发布帧而不是让 CEF paint 直接丢失观测。短期至少要加丢帧计数、锁等待/失败计数和发布耗时日志，先把延迟来源量化。

### Headless 关闭顺序允许 OnPaint 访问已释放 Capture

定性：违反硬性工程基线。

证据：

- `HeadlessBrowser/HeadlessBrowser/PageHandler.cs:605` 进入 `Unload()`。
- `HeadlessBrowser/HeadlessBrowser/PageHandler.cs:621` 先执行 `_CaptureMemory?.Dispose()`。
- `HeadlessBrowser/HeadlessBrowser/PageHandler.cs:638` 之后才执行 `browserHost.CloseBrowser(true)`。
- `HeadlessBrowser/HeadlessBrowser/PageHandler.cs:295` 的 `OnPaint()` 没有先检查 `State` 或 `_CaptureMemory == null`，后续会使用 `_CaptureMemory`。

风险：

CEF browser 在关闭前后仍可能触发 paint 或其他回调。当前顺序可能导致空引用、ObjectDisposed 异常、关闭流程不稳定、进程残留或退出告警。这个问题和“停止调试后仍有进程占用”的生命周期问题属于同一类风险。

建议：

关闭流程应先阻止或断开渲染回调，再请求 CEF browser close，确认 `OnBeforeClose` 或等价关闭事件后释放 Capture。`OnPaint` 也应增加快速保护：未运行、关闭中、`_CaptureMemory == null` 或已释放时直接返回。

### 模块销毁没有等待轮询任务退出

定性：违反硬性工程基线。

证据：

- `HeadlessBrowser/HeadlessBrowser/Modules/MemoryModuleBase.cs:46` 使用 `while (State)` 启动轮询。
- `HeadlessBrowser/HeadlessBrowser/Modules/MemoryModuleBase.cs:87` 的 `Destroy()` 只设置状态并关闭栈，没有等待任务结束。
- `HeadlessBrowser/HeadlessBrowser/PageHandler.cs:650` 在页面卸载时连续调用 `module.Destroy()`。

风险：

卸载时模块可能仍在跑最后一轮读写或投递 CEF 任务，随后 Capture、browser host 或共享内存已经释放。这会放大输入延迟、关闭竞态和进程残留风险。

建议：

模块生命周期改为可等待的 `StartAsync/StopAsync` 或持有任务句柄与取消令牌。`Unload()` 必须有明确顺序：停止输入/脚本模块，等待关键任务退出，请求 browser close，最后释放共享内存。

### Unity UPM 包依赖清单与实际代码引用不一致

定性：违反硬性工程基线。

证据：

- `BrowserRenderer/Assets/Packages/package.json:12` 只声明少量 package dependencies。
- `BrowserRenderer/Packages/manifest.json:4`、`:11`、`:12`、`:13` 声明了 `org.nuget.globalconfigs`、`org.nuget.memorystacks`、`org.nuget.singletons`、`org.nuget.superevents`。
- `BrowserRenderer/Assets/Packages/Scripts/BrowserHandler.cs:8` 引用 `KimoTech.GlobalConfigs`。
- `BrowserRenderer/Assets/Packages/Scripts/MemoryModules/MemoryModuleBase.cs:5` 引用 `KimoTech.MemoryStacks`。
- `BrowserRenderer/Assets/Packages/Scripts/ProcessHandler.cs:9` 引用 `KimoTech.SuperEvents`。

风险：

`Assets/Packages` 作为独立 UPM 包被其他 Unity 工程安装时，会依赖宿主工程碰巧安装这些 NuGet bridge 包。包边界不可信，发布和复用时容易直接编译失败。

建议：

把 `Assets/Packages/package.json` 作为发布边界的唯一依赖声明，补齐运行时代码直接引用的依赖。宿主工程 `Packages/manifest.json` 只能表达示例工程依赖，不应替代 UPM 包自身依赖。

### Runtime assembly 全局打开 unsafe，内存风险边界过宽

定性：规范缺失导致风险。

证据：

- `BrowserRenderer/Assets/Packages/Scripts/KimoTech.EmbeddedBrowser.asmdef:11` 设置 `"allowUnsafeCode": true`。
- 实际需要 unsafe 的高风险代码集中在 `BrowserRenderer/Assets/Packages/Scripts/MemoryModules/CaptureSharedMemory.cs` 的指针拷贝和共享内存访问。
- 同一个 runtime assembly 同时包含 `PageRenderer`、`BrowserStatic`、输入、IME、进程管理等上层业务适配代码。

风险：

为了一个底层共享内存模块放开整个 Runtime assembly 的 unsafe 权限，会扩大后续审查范围。任何运行时代码都可以继续引入 unsafe，质量门禁无法隔离高风险内存操作。

建议：

拆出专用 `KimoTech.EmbeddedBrowser.Memory` 或 `KimoTech.EmbeddedBrowser.Native` asmdef，只在该 assembly 启用 unsafe。上层 `PageRenderer/PageHandler` 通过安全 C# API 使用共享内存。

### PageRenderer 职责过重，Unity 生命周期组件边界不清

定性：规范缺失导致风险。

证据：

- `BrowserRenderer/Assets/Packages/Scripts/PageRenderer.cs:43` 进入组件启动。
- `BrowserRenderer/Assets/Packages/Scripts/PageRenderer.cs:60` 直接向 `BrowserStatic` 注册页面。
- `BrowserRenderer/Assets/Packages/Scripts/PageRenderer.cs:101` 的 `LateUpdate` 串联重启、尺寸、鼠标、IME、键盘、纹理拷贝和 Apply。
- `BrowserRenderer/Assets/Packages/Scripts/PageRenderer.cs:303` 的销毁逻辑继续处理 page handler、texture 和进程侧删除协议。

风险：

`PageRenderer` 同时承担 Unity UI 适配、页面协议、输入同步、IME、Capture 应用、纹理生命周期和重启恢复。性能问题、销毁顺序和协议问题都集中在一个 MonoBehaviour 中，难以单测，也容易在修复一个链路时破坏另一个链路。

建议：

保留 `PageRenderer` 作为 RawImage/Unity 事件适配层，把页面生命周期、输入同步、Capture 应用和重启恢复拆成明确协作者。`PageHandler` 应暴露稳定页面状态机，不让 `PageRenderer` 直接编排所有底层模块。

### Unity 页面销毁顺序先销毁本地模块再发 RemovePage

定性：违反硬性工程基线。

证据：

- `BrowserRenderer/Assets/Packages/Scripts/PageRenderer.cs:313` 先 `_Handler?.Destroy()`。
- `BrowserRenderer/Assets/Packages/Scripts/PageRenderer.cs:317` 后调用 `BrowserStatic.Instance.RemovePage(GUID)`。
- `BrowserRenderer/Assets/Packages/Scripts/PageHandler.cs:185` 到 `:192` 中 `Destroy()` 会销毁 Capture、鼠标、脚本、键盘、IME、Caret 和 surrounding text 模块。
- `BrowserRenderer/Assets/Packages/Scripts/BrowserStatic.cs:136` 的 `RemovePage` 负责向浏览器进程发送删除页操作。

风险：

本地通信模块先释放，浏览器进程里的页面删除指令后发。快速销毁、停止播放或重启时，容易形成旧页面残留、删除指令丢失或异常被吞掉。

建议：

定义单一 `ClosePage` 流程：先通过 `BrowserStatic/PageRegistry` 发送 RemovePage 并更新注册表，再释放本地页面模块；或者把 fire-and-forget 行为封装到一个明确协议入口中，避免销毁顺序散落在 `PageRenderer.OnDestroy`。

### HeadlessBrowser 测试入口没有覆盖真实主链路

定性：规范缺失导致风险。

证据：

- `HeadlessBrowser/HeadlessBrowser.Tests/HeadlessBrowser.Tests.csproj:6` 关闭 nullable，且项目没有常规测试框架/runner 依赖。
- 当前测试主要是手写 console 程序和纯函数检查，未覆盖真实 `CaptureSharedMemory` 写入布局、ack 读写、非阻塞锁丢帧、MouseState 线程派发、Unload 竞态。

风险：

最容易回归的恰好是跨进程 capture、mouse 和 lifecycle 主链路。现有测试无法防止后续再次出现鼠标延迟、画面拼接和退出残留。

建议：

保留轻量 console 测试可以，但必须增加可自动化的最小测试：capture writer/reader 协议、ack 门控、未 ack 回退 full frame、MouseState 派发策略、Unload 后 OnPaint 不触碰已释放 capture。

### .NET 项目关闭 nullable 且 unsafe 缺少更细边界

定性：规范缺失导致风险。

证据：

- `HeadlessBrowser/HeadlessBrowser/HeadlessBrowser.csproj:7` 为 `<Nullable>disable</Nullable>`。
- `HeadlessBrowser/HeadlessBrowser/HeadlessBrowser.csproj:8` 为 `<AllowUnsafeBlocks>true</AllowUnsafeBlocks>`。
- `HeadlessBrowser/HeadlessBrowser.Tests/HeadlessBrowser.Tests.csproj:6` 同样关闭 nullable。

风险：

HeadlessBrowser 当前有大量生命周期、跨线程、可释放对象和共享内存逻辑。关闭 nullable 会弱化 `_CaptureMemory`、`_BrowserHost`、模块引用等对象生命周期的静态约束；项目级打开 unsafe 会让未来高风险代码扩散到非内存边界。

建议：

逐步开启 nullable，先从新文件和共享内存/生命周期相关类型开始。unsafe 也应和 Unity 侧一样收敛到共享内存底层类型，不在整个应用项目范围内默认放开。

### 文档与当前实现漂移

定性：违反项目已确认规范。

证据：

- `HeadlessBrowser/README.md:3` 仍写“基于 CefSharp.OffScreen”。
- `HeadlessBrowser/README.md:22`、`:80` 仍使用 `ChromiumWebBrowser` 描述。
- `HeadlessBrowser/README.md:93` 仍描述 `Marshal.Copy` 到预分配缓冲区。
- `HeadlessBrowser/README.md:262`、`:263` 依赖表仍写 `CefSharp.OffScreen.NETCore` 和 `MemoryStacks 0.2.2`。
- 实际 `HeadlessBrowser/HeadlessBrowser/HeadlessBrowser.csproj:23` 注释已写“CefGlue 替代 CefSharp”，`:24` 使用 `CefGlue.Common 120.6099.211`，`:25` 使用 `MemoryStacks 0.2.9`。
- `BrowserRenderer/Assets/Packages/package.json:6` 和 `BrowserRenderer/README.md:241` 写 Unity 2019.4，但 `BrowserRenderer/ProjectSettings/ProjectVersion.txt:1` 是 Unity `2021.3.58f1`。
- `BrowserRenderer/BrowserConfig.json:3` 使用 `"GraphicsMode": "True"`，而 README 描述支持值为 `Auto/Off/On`；`BrowserRenderer/Assets/Packages/Scripts/BrowserHandler.cs:42` 起的归一化逻辑只明确处理 `off/on`，其他值会回到 `auto`。

文档会把后续排查带回 CefSharp、旧 MemoryStacks、旧渲染管线和错误配置语义。`GraphicsMode=True` 还会让人误以为强制启用图形，实际代码语义更接近 `auto`。

更新 README、package metadata 和配置示例，明确当前为 CefGlue、dirty rect + ack 协议、当前最低 Unity 版本、真实依赖版本和 `GraphicsMode` 合法值。若要保留 `True/False`，代码和文档都要显式支持并说明映射语义。

### 聚合目录缺少统一产物治理边界

定性：规范缺失导致风险。

证据：

- 根目录不是 Git 仓库，`BrowserRenderer`、`HeadlessBrowser`、`native-ime`、`MemoryStacks` 等独立管理。
- `headless_browser` 不是 Git 仓库，但存在 `target/`。
- `BrowserRenderer/NativePlugins/process-spawner/target`、`native-ime/target`、`headless_browser/target` 均存在。
- `headless_browser/.gitignore:3` 忽略 `Cargo.lock`，但目录内实际存在 `Cargo.lock`，规则和当前文件状态不一致。
- `headless_browser/README.md:26` 仍标记“测试部署（待开始）”，但该目录同时已有大量 `target` 产物。

风险：

聚合目录级扫描和评审会反复钻入 Unity `Library`、Rust `target`、.NET `bin/obj` 等生成目录，拖慢检查并污染判断。旧 Rust 浏览器目录缺少明确仓库边界，也容易让人误判它是否仍是正式实现。

建议：

给聚合工作区补充顶层说明或治理文档：哪些子目录是正式仓库，哪些是旧实现或实验目录；统一列出应排除的生成目录。旧 `headless_browser` 要么纳入正式 Git 管理并补齐治理，要么标记为归档/实验并从主链路文档中移除。

## 整改优先级建议

### 第一阶段：收敛鼠标延迟和画面撕裂主链路

- 修复 `MouseStateModule`：mouse move 统一投递 CEF UI 线程，并做 latest-only 合并，避免积压历史移动事件。
- 重构 Capture 发布策略：paint 回调只更新进程内 latest buffer，独立发布器写共享内存；至少先补丢帧、锁竞争和发布耗时计数。
- 调整 Headless `Unload()` 顺序：先关闭 browser/断开 paint，再释放 Capture；`OnPaint` 增加关闭态保护。
- 给鼠标、Capture、Unload 增加最小自动化测试，覆盖本次风险点。

### 第二阶段：稳定进程和页面生命周期

- 把 Headless 模块生命周期改为可等待停止，避免 `Destroy()` 后还有轮询任务继续跑。
- 统一 Unity 侧 `ClosePage` 流程，先发 RemovePage，再释放本地模块。
- 给停止播放、重启浏览器、快速创建销毁页面增加诊断日志和测试入口。
