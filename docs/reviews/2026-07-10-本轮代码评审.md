# Lichora 本轮代码评审报告

## 评审范围

本报告审查本轮会话产生的全部未提交改动：仓库级质量脚本、插件发布契约、Rust 入口拆分、overlay 类型与包契约、Unity Native/Protocol/Model 程序集拆分和相关文档。

本报告是 `docs/reviews/2026-07-10-工程体系评审.md` 的代码变更专项审查。由于前一份报告评审的是改动前工程基线，本报告单独记录本轮实现引入的具体回归，避免覆盖原始评审依据。

本次不启动 Unity Editor、Unity batchmode、BuildPipeline 或 Unity Test Framework，也不使用 Unity 生成的 `.sln`、`.csproj` 做外部编译。

## 总体结论

本轮方向基本正确：Rust `main.rs` 已收敛为组合入口，CLI 与 Unity handler 分开；overlay 增加了类型检查和包契约；插件 manifest 和统一质量入口让部分人工约定转为可执行检查；Unity 的 Model、Protocol、Native 目录也表达了预期依赖方向。

当前变更不能交付。Unity 程序集拆分存在两个阻断级错误：Runtime 对原第三方程序集的 GUID 被错误改写；Runtime 又直接访问 Native 程序集中的多项 `internal` 类型，且没有友元程序集声明。这两项都会导致 Unity 程序集解析或 C# 编译失败。现有 `check-quality.ps1` 和 `check-plugin-contract.ps1` 均返回通过，说明新增门禁尚不能验证其声称守住的程序集契约。

Rust 和 overlay 改动未发现阻断性回归。当前优先级应是修复 Unity 编译边界，并让静态契约脚本能够复现这两类错误；在此之前不应继续扩大程序集拆分范围。

## 主要问题

### Native 程序集的内部类型无法被 Runtime 访问

- **级别：高。定性：架构边界失效，程序集迁移不完整。**
- `hosts/unity-host/Scripts/Native/BrowserIpcNative.cs:9` 将 `BrowserIpcNative` 声明为 `internal`；`NativeIpcHandle`、`NativeIpcResult`、`NativeIpcErrorCode`、`NativeIpcSessionOptions` 和 `NativeImeBridge` 等类型也保持 `internal`。
- Runtime 中的 `hosts/unity-host/Scripts/Ipc/BrowserIpcClient.cs:7`、`hosts/unity-host/Scripts/Ipc/BrowserIpcFrameReader.cs:8`、`hosts/unity-host/Scripts/Ipc/BrowserIpcInputWriter.cs:7` 等文件直接使用这些类型。
- 仓库没有 `InternalsVisibleTo("KimoTech.LichoraHost")`，程序集拆分后原先同程序集内合法的访问会变成跨程序集不可访问。
- 风险是 Unity C# 编译直接失败；CSharpier 和文本契约检查无法证明程序集可编译。
- 建议先确定唯一边界：优先让 Native 提供最小公开 facade/handle API，Runtime 不直接穿透所有内部实现；若当前阶段只做物理拆分，可暂时使用受控的 `InternalsVisibleTo`，并在契约检查中验证友元目标和依赖方向。

### Runtime 和 Native 引用了错误的第三方程序集 GUID

- **级别：高。定性：违反项目已确认配置，程序集引用回归。**
- 基线 `hosts/unity-host/Scripts/KimoTech.LichoraHost.asmdef` 引用 `GUID:3dcbb65762ae01440b7e7f4a08bf32bd`，Editor asmdef 当前也仍使用该 GUID。
- 本轮改动把 Runtime 和 Native 中的对应引用写成 `GUID:3dcbb65762ae01440a699833d6309b23`，见 `hosts/unity-host/Scripts/KimoTech.LichoraHost.asmdef:8` 和 `hosts/unity-host/Scripts/Native/KimoTech.LichoraHost.Native.asmdef:6`。
- 新 GUID 在仓库及基线历史中没有来源，属于改写 asmdef 时引入的值漂移。
- 风险是 Unity 报缺失程序集引用；Native 中 `Unity.Collections`、`Unity.Collections.LowLevel.Unsafe` 等依赖也无法可靠解析。
- 建议恢复已确认 GUID，并让插件契约脚本校验关键第三方引用没有被替换；不要只校验新增程序集之间的 GUID。

### 质量脚本会漏掉未跟踪的 Unity C# 文件

- **级别：中。定性：静态检查覆盖不完整。**
- `scripts/check-quality.ps1:42` 使用 `git ls-files "hosts/unity-host/**/*.cs"` 收集文件，只包含 Git 已跟踪文件。
- 当前本轮新增的 Model、Protocol、Native 共 12 个 C# 文件仍未跟踪；全量脚本因此只报告检查 40 个文件，而 `hosts/unity-host/Scripts` 当前实际有 51 个 C# 文件。
- 本轮通过额外的手工 `csharpier check` 覆盖了新增文件，但统一入口自身仍会在开发者暂存前漏检新文件，且输出“Quality checks passed”。
- 建议从受控源码目录扫描现存 `.cs`，明确排除生成目录；或合并已跟踪文件与 `git ls-files --others --exclude-standard`。

### 插件契约脚本无法识别程序集阻断错误

- **级别：中。定性：验证路径可信度不足。**
- `scripts/check-plugin-contract.ps1` 能检查 Model/Protocol/Native asmdef 的名称、部分依赖方向和文件位置，但没有检查 Runtime 对 Native 内部类型的跨程序集访问，也没有验证第三方 asmdef GUID 是否来自已确认依赖。
- 本轮两个高风险问题存在时，`check-plugin-contract.ps1` 和 `check-quality.ps1` 仍均返回通过。
- 脚本当前更接近“目录和 manifest 一致性检查”，不能作为 Unity 程序集可编译契约的替代证明。
- 建议增加可静态执行的程序集边界规则：跨程序集使用的类型必须公开或具备明确友元声明；关键 asmdef 引用必须匹配已确认 GUID。

### Protocol 的无 Unity 依赖边界没有配置约束

- **级别：中。定性：文档与可执行约束不一致。**
- `docs/development.md` 和 `hosts/unity-host/README.md` 将 Protocol 描述为无 Unity 依赖程序集。
- `hosts/unity-host/Scripts/Protocol/KimoTech.LichoraHost.Protocol.asmdef:13` 的 `noEngineReferences` 仍为 `false`；契约脚本只检查 `references.Count == 0` 和 `autoReferenced == false`。
- 当前 Protocol 源码没有 `UnityEngine` 使用，因此现状符合描述；配置没有阻止后续代码重新引入 UnityEngine。
- 建议把 `noEngineReferences` 设为 `true`，并在契约脚本中强制检查。

### Protocol 拆分扩大了公开 API 面

- **级别：中。定性：公共契约扩大但缺少明确决策。**
- 为满足 Runtime/Native 跨程序集访问，`BrowserIpcInputPayload`、`BrowserIpcOutputPayload` 及其 payload struct/enum 从 `internal` 改为 `public`。
- 这些类型随 Unity Package 成为宿主工程可直接访问的公共 API，后续字段、编码细节和类型命名会承担兼容成本。
- 建议明确 Protocol 是否是公开 SDK。若仅供包内部使用，使用受控友元程序集并保留 `internal`；若决定公开，则补充 API 稳定性和版本策略。

### 插件 manifest 尚未形成可追溯制品契约

- **级别：中。定性：发布治理仍不完整。**
- `hosts/unity-host/Plugins/plugin-manifest.json` 已记录平台、架构、P/Invoke 名、source crate 和 release 状态，是有效进展。
- `process-host` 和 `native-ime` 的 `abiVersion` 为 `null`；manifest 没有构建提交、构建配置或校验值，脚本只检查字段存在。
- README 将校验值交给未来发布自动化，但仓库当前没有对应发布入口。
- 建议在真实发布链路中生成来源、提交、配置和校验信息；当前不要手写无法验证的 hash。

## 已确认改进

### Rust 入口职责已明显收敛

- `src/main.rs` 从约 730 行缩减到约 100 行，保留 CEF 子进程分流、日志初始化、组合启动和单浏览器循环。
- CLI 解析、graphics mode 和参数测试迁入 `src/cli.rs`；handler 控制队列、命令分发和运行日志迁入 `src/handler.rs`。
- 对照基线执行链未发现明显语义丢失；无 CEF 的全部 target 测试通过。

### Overlay 增加了可信的静态入口

- `packages/overlay/package.json` 增加 `typecheck`、`check-package` 和统一 `check`。
- `packages/overlay/tsconfig.json` 启用 strict 和 noEmit；包契约脚本验证 exports、files 和入口文件存在性。
- 19 个现有行为测试、类型检查和包契约均通过。真实浏览器/CEF 集成验证仍不在该入口覆盖范围内。

### Model 边界保持了最小化

- 仅将 `InputOwner` 和 `InputRegionShape` 迁入无依赖 Model 程序集，并保留原脚本 `.meta` GUID。
- `InputRegion`、`InputOwnershipMap` 和 render snapshot 继续留在 Runtime，符合其 Unity 序列化和坐标类型依赖。

## 当前整改状态

- 已恢复 Runtime 和 Native 的正确 Unity.Collections GUID。
- IPC client/readers/writers 已整体迁入 Native，Runtime 只依赖公开 facade；raw handle、result、P/Invoke 和 input codec 保持 internal。
- Linux IME 编排已回到 Runtime，新增 `NativeImeClient` 隔离原生 ABI 和事件缓冲。
- Runtime 已关闭 unsafe；Protocol 已启用 `noEngineReferences`；Native 不再依赖 Protocol 或 Runtime 业务程序集。
- CSharpier 入口已改为扫描全部现存 Unity Scripts，包括未跟踪的新源码。
- 静态契约脚本已增加关键 GUID、依赖方向、公开 facade、internal implementation 和 Runtime 穿透检查。
- 以上状态仍未经过 Unity Editor 导入或 Unity 内程序集编译验证。
## 整改优先级建议

### 先恢复 Unity 可编译边界

- 恢复正确第三方程序集 GUID。
- 明确 Native 对 Runtime 的公开 facade 或友元策略，消除跨程序集 `internal` 访问错误。
- 将 Protocol 的 `noEngineReferences` 与文档声明对齐。

### 再提高门禁可信度

- 让 CSharpier 收集全部现存源码，包括未跟踪的新文件。
- 增加关键 GUID、友元程序集和跨程序集可见性检查。
- 将脚本输出准确表述为静态契约结果，避免暗示 Unity 编译已经验证。

### 最后收口发布治理

- 明确 Protocol 的公共 API 边界和兼容策略。
- 为原生制品补充可由发布流程生成的来源、提交、配置和校验信息。
- 在具备运行环境后补 Unity 导入、编译及真实插件加载验证。
