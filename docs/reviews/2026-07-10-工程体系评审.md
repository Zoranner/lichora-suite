# Lichora 工程评审报告

## 评审范围

本次评审覆盖仓库工程结构、目录结构、Rust workspace 与 IPC crate 边界、Unity Package 组织、Web overlay SDK、跨进程架构、代码规范、测试与验证入口、构建发布和仓库治理。

本次不评价具体功能需求是否完成，也不启动 Unity Editor、不运行 Unity batchmode、BuildPipeline、Unity Test Framework batchmode，不使用 Unity 生成的 `.sln`/`.csproj` 编译。

## 评审依据

- 仓库根目录的 `README.md`、`docs/development.md`、`docs/protocol.md` 和 `docs/design/web-host-overlay.md`。
- 根目录 `Cargo.toml`、各 crate 的 `Cargo.toml`、`package.json`、`.gitignore`、`.gitmodules` 和 `build.ps1`。
- `review-engineering` 通用工程基线，以及 Rust、Unity 专项检查项。
- 当前仓库事实、源码静态检查结果、Git 状态和现有测试入口。

## 总体结论

项目已经形成清晰的主链路：Rust CEF runtime、`lichora-ipc` IPC core、原生 C ABI、Unity host 和 Web overlay SDK 分层存在，IPC v2 的通道模型和 ownership 语义也有对应文档与测试支撑。当前工作树干净，Rust 格式和 Clippy 门禁通过，overlay 单元测试通过。

主要工程风险不在“没有模块”，而在“模块已存在但部分边界还没有成为可执行约束”：根 Rust 应用入口仍承载较多 handler、CLI、IPC 和运行循环职责；Unity Runtime asmdef 把平台原生桥接、IPC、输入、渲染和页面生命周期放进同一程序集；C ABI 和平台插件依赖较多人工约定；Unity 包没有包级测试与自动化格式门禁；原生二进制已直接进入 Git，但缺少 ABI、来源、架构和校验治理；文档中仍保留聚合工作区历史材料，增加新成员理解正式主链路的成本。

建议先收口可执行边界和发布契约，再考虑进一步拆 crate 或重写模块。当前不建议继续增加新的抽象层或服务。

## 主要问题

### Runtime asmdef 没有形成平台与职责边界

- **定性：规范缺失导致风险；架构边界不足。**
- `hosts/unity-host/Scripts/KimoTech.LichoraHost.asmdef:2-17` 将 IPC、进程管理、IME、输入、ownership、渲染和页面生命周期全部编入一个 Runtime 程序集，`includePlatforms` 为空，`allowUnsafeCode` 为 `true`。
- `NativeProcessSpawner.cs`、`NativeImeBridge.cs`、`Ipc/BrowserIpcNative.cs` 中的 P/Invoke 声明因此和普通 Runtime 类型处于同一编译边界，当前主要依赖运行时平台判断与插件 `.meta` 配置兜底。
- 风险是新增平台、插件 importer 漂移或错误引用时，平台不支持问题只能在运行时暴露；目录分层没有转化为编译依赖约束，原生 ABI 也没有独立的可替换边界。
- 建议按实际替换边界拆成协议/纯 C#、Runtime host、平台原生桥接三个程序集，或至少通过平台 define 和独立平台程序集隔离原生入口。不要为了“分层完整”机械增加 asmdef。

### 根 Rust 应用入口职责过重

- **定性：建议优化；当前已形成可维护性风险。**
- `src/main.rs:14-95` 负责 CEF 子进程分流、日志初始化、参数解析、单浏览器启动、消息循环和退出；`src/main.rs:97-315` 继续承载 Unity handler 生命周期、控制队列打开、命令分发和浏览器表维护；`src/main.rs:416-699` 又包含 CLI 配置、图形模式、参数解析和使用说明。
- `src/main.rs` 约 800 行，启动组合、handler orchestration、CLI 解析和 IPC 适配混在一个文件中。
- 风险是新增 handler 命令、生命周期状态或 CLI 选项会继续扩大入口文件，测试需要穿过更多全局运行逻辑；入口层难以作为纯组合根复用。
- 建议将 CLI 模型/解析、handler runtime、控制命令分发和运行日志分别收敛到 `src/cli.rs`、`src/handler/`、`src/runtime/` 等职责边界，`main.rs` 只保留启动组合和顶层错误处理。

### C ABI 与平台进程管理边界依赖人工契约

- **定性：规范缺失导致风险。**
- `crates/lichora-ipc-native/src/lib.rs:54-71` 起集中暴露大量 `unsafe extern "C"` 函数，函数内部多处直接处理裸指针、长度和 opaque handle；`crates/process-host/src/lib.rs:22-37` 通过裸指针转换字符串并暴露平台进程操作。
- 当前 `cargo clippy --all-targets --all-features -- -D warnings` 通过，说明代码满足现有 lint，但不等于 C ABI 的调用前提、句柄生命周期、线程约束和指针所有权已经形成机器可检查契约。
- 风险是 Unity 侧 ABI 字段、错误码、句柄关闭顺序或调用线程发生漂移时，问题可能表现为 native 崩溃或资源泄漏，而不是可诊断的业务错误。
- 建议为每组 C ABI 增加稳定头文件/导出清单、ABI 版本常量、句柄状态约束和跨语言 golden contract；把裸指针转换集中在少量内部 helper 中，并为 double-close、空指针、超长 payload、错误 session 和跨线程调用补测试。

### Unity 平台插件支持面没有自动化契约

- **定性：规范缺失导致风险。**
- Linux IPC 插件的 importer 状态位于 `hosts/unity-host/Plugins/Linux/liblichora_ipc_native.so.meta:17-65` 等 `.meta` 文件；Windows 与 Linux 插件配置、P/Invoke 名称、`build.ps1` 复制逻辑和 `hosts/unity-host/README.md:12-31` 分散维护。
- 当前版本明确限制 Linux IPC 发布面，这是有效产品约束，但仓库没有发现平台支持矩阵或脚本检查来验证“插件文件存在、`.meta` importer 状态、代码入口、构建产物和 README 声明”一致。
- 风险是发布配置改变后，静态代码、插件 importer 和文档可能分别表达不同支持面，直到宿主项目导入或运行时才暴露。
- 建议建立平台矩阵，并增加不启动 Unity 的静态检查：校验目标文件、架构标记、P/Invoke 名称、`.meta` 平台状态、构建脚本复制目标和文档声明。

### Unity 包共用一个 Runtime 程序集，目录层级没有转化为依赖约束

- **定性：建议优化。**
- `Scripts/Input`、`Scripts/Ipc`、`Scripts/Ownership`、`Scripts/Rendering`、`Scripts/Runtime` 以及根目录页面/进程脚本均由 `KimoTech.LichoraHost.asmdef` 覆盖。
- 目录对阅读有帮助，但无法阻止 IPC 层反向依赖渲染、平台原生代码被普通 Runtime 类型引用，或高频变化模块扩大整个程序集的重新编译范围。
- 建议根据真实变化和替换边界逐步拆分，不要继续通过文件夹层级制造“看起来分层”。优先隔离协议与纯计算逻辑、平台原生桥接、Unity 渲染/生命周期三个边界。

### Unity 资源和序列化配置边界偏弱

- **定性：规范缺失导致风险。**
- `hosts/unity-host/Scripts/Rendering/BrowserRenderSettings.cs:7` 固定材质路径，`hosts/unity-host/Scripts/Rendering/BrowserSurface.cs:201-209` 通过 `Resources.Load<Material>` 加载 `Resources/Materials/BrowserRender.mat`。
- `hosts/unity-host/Scripts/PageRenderer.cs:26-30` 直接公开 `Address`、`FilteredColor`、`TransparencyMode`；`BrowserRenderSettings.cs:45-54` 仍保留旧字段到新模式的兼容转换。
- `Resources` 会把材质放入 Unity 全局索引，显式依赖关系不清晰；旧配置和新配置并存时，Prefab/场景序列化数据的优先级也不够明确。
- 建议优先使用显式序列化引用或资源提供器；如果暂时保留 `Resources`，应文档化路径、覆盖规则和加载失败行为。配置字段应统一为私有序列化字段 + 属性，并通过 `[FormerlySerializedAs]` 管理迁移。

### Unity 原生二进制缺少版本、来源和存储治理

- **定性：规范缺失导致风险。**
- Git 直接跟踪 `hosts/unity-host/Plugins/Windows/*.dll`、`hosts/unity-host/Plugins/Linux/*.so`，其中 `libnative_ime.so` 约 3.1 MB；仓库没有发现 `.gitattributes` 或 Git LFS 规则，也没有看到 ABI、目标架构、构建来源和校验清单。
- `build.ps1:111-158` 会把构建产物复制到 Unity 插件目录，但没有生成版本清单、SHA-256 或 ABI 兼容信息。
- 风险是二进制和源码提交容易漂移，无法快速判断插件是否由当前 Rust 源码生成，也无法对发布包做可重复核验。
- 建议至少增加插件 manifest，记录 crate 版本、目标平台/架构、导出 ABI 版本、构建提交和校验值；再根据团队仓库策略决定 Git LFS 或外部制品仓库。

### Unity 包缺少包级测试和自动化规范门禁

- **定性：规范缺失导致风险。**
- `hosts/unity-host` 下未发现 `Tests/`、测试程序集或测试脚本；协议 payload、坐标映射、ownership 判定、键盘映射和配置转换存在可独立测试的逻辑。
- 当前 `csharpier check` 的 51 个文件通过，但仓库没有 `.csharpierrc*`、`.csharpierignore` 或 CI 工作流，检查结果无法自动成为提交门禁。
- 风险是纯 C# 回归只能在宿主项目或运行时才发现，格式与命名规范依赖开发者本机自觉。
- 建议先增加不依赖 Unity Editor 的协议/映射/配置测试，再补 Unity EditMode/PlayMode 测试；同时把 CSharpier 检查、Rust fmt/clippy、Bun test 纳入统一 CI。

### overlay SDK 的验证入口偏窄，缺少类型和发布门禁

- **定性：规范缺失导致风险。**
- `packages/overlay/package.json:1-24` 只定义 `bun test`，没有 `typecheck`、lint、构建产物校验或 API contract 检查。
- 当前 `src/index.test.ts` 有 19 个测试并全部通过，已覆盖 bridge、ownership 注册、区域过滤、observer 调度和 host surface 透明化；但没有独立的类型检查和浏览器真实 DOM/CEF bridge 集成验证入口。
- 风险是测试可以通过而公开导出类型、编译目标、打包 exports 或真实浏览器行为发生漂移。
- 建议增加 `bun x tsc --noEmit` 或等价 Bun 兼容类型检查、lint 和最小打包检查；把 bridge payload 与 Rust/Unity 解码契约纳入跨语言 golden test。当前不建议复制一套 demo ownership 逻辑，示例应继续复用 SDK 主链路。

### 历史聚合工作区文档仍位于正式 docs 树

- **定性：规范缺失导致风险。**
- `docs/archive/aggregate-workspace/` 包含旧聚合工作区架构、评审和 archive README；其中材料仍引用 `headless_browser`、旧仓边界和历史目录治理。
- 当前 `docs/development.md` 与 `README.md` 已把 `lichora-suite` 主链路描述为 Rust + Unity host + overlay，但新成员在 `docs/` 下搜索架构时仍会同时看到旧实现和正式说明。
- 风险是历史材料被误认为当前架构依据，导致目录、仓库边界和构建入口理解错误。
- 建议在 `docs/archive/aggregate-workspace/README.md` 明确“仅供历史追溯，不作为当前架构依据”，并在正式文档入口增加当前文档导航；旧材料中不再维护当前实现细节。

### Editor 和 Sample 命名边界不完整

- **定性：低风险规范缺失。**
- `hosts/unity-host/Scripts/Editor/KimoTech.LichoraHost.Editors.asmdef:2-18` 的 `rootNamespace` 为空，而 Editor 脚本使用 `KimoTech.LichoraHost.Editors` 命名空间。
- `hosts/unity-host/Samples~/ECharts/ScriptSender.cs:6-10` 使用全局命名空间，并直接暴露公共字段；Sample 没有独立 asmdef 或命名约束。
- 风险暂时局部，主要表现为导入宿主工程后潜在类型名冲突和命名漂移。
- 建议设置 Editor asmdef 的 `rootNamespace`，Sample 使用 `KimoTech.LichoraHost.Samples` 命名空间；是否增加 Sample asmdef 取决于其依赖和 Unity 最低版本。

## 整改优先级建议

### 第一阶段：把跨语言和平台契约变成可检查规则

- 建立 Windows/Linux 支持矩阵，校验插件文件、`.meta` importer、P/Invoke 名称、导出函数和 README 声明。
- 为 native 插件生成版本/ABI/架构/提交/校验 manifest。
- 增加 C ABI 句柄生命周期、错误码、空指针和 payload 边界的跨语言 contract test。
- 将 Rust fmt/clippy、overlay test、CSharpier 和静态插件检查纳入 CI。

### 第二阶段：收紧 Unity 和 Rust 的职责边界

- Unity 先拆协议/纯 C#、平台原生桥接、Runtime host 三类边界，再根据实际依赖决定是否继续拆渲染和 ownership。
- Rust 将 `main.rs` 中的 CLI、handler orchestration、控制命令分发和运行日志拆出，保持 `main.rs` 为组合根。
- 统一错误、句柄和关闭语义，避免平台差异继续扩散到业务模块。

### 第三阶段：治理资源、二进制和文档入口

- 明确 `Resources` 材质的加载策略和宿主覆盖规则，逐步减少隐式全局资源。
- 为 Unity 插件二进制确定 Git LFS 或制品仓库策略，并清理无来源、无校验的替换路径。
- 完善当前文档导航，明确 archive 只用于历史追溯，避免旧聚合工作区材料与正式架构并列误导。
